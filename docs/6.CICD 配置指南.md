## 概述

项目使用 GitHub Actions 实现 CI/CD 自动化，包括：

- ✅ 自动化测试（单元测试、集成测试）
- ✅ 代码质量检查（Lint、类型检查）
- ✅ 安全扫描（依赖漏洞、代码扫描）
- ✅ Docker 镜像构建和推送
- ✅ 自动化部署（Staging、Production）
- ✅ 依赖更新检查
- ✅ 自动代码审查

## 工作流说明

### 1. CI - 持续集成 (`.github/workflows/ci.yml`)

**触发条件：**
- Push 到 `main` 或 `develop` 分支
- 创建或更新 Pull Request

**执行任务：**

#### 后端测试 (backend-test)
- 代码格式检查 (`npm run lint`)
- TypeScript 类型检查 (`npm run type-check`)
- 运行数据库迁移
- 单元测试 (`npm run test:unit`)
- 集成测试 (`npm run test:integration`)
- 生成测试覆盖率报告
- 上传覆盖率到 Codecov

**依赖服务：**
- PostgreSQL 15
- Redis 7

#### 前端测试 (frontend-test)
- 代码格式检查 (`npm run lint`)
- TypeScript 类型检查 (`npm run type-check`)
- 单元测试 (`npm run test:unit`)
- 生成测试覆盖率报告
- 上传覆盖率到 Codecov
- 构建检查 (`npm run build`)

#### 代码质量检查 (code-quality)
- 安装依赖
- 可选：SonarCloud 代码质量分析

#### Docker 镜像构建测试 (docker-build)
- 构建后端 Docker 镜像
- 构建前端 Docker 镜像
- 使用 GitHub Actions 缓存加速构建

#### 安全扫描 (security-scan)
- Trivy 漏洞扫描
- 后端依赖安全审计 (`npm audit`)
- 前端依赖安全审计 (`npm audit`)

### 2. CD - 持续部署 (`.github/workflows/cd.yml`)

**触发条件：**
- Push 到 `main` 分支
- 创建版本标签 (`v*`)
- 手动触发 (workflow_dispatch)

**执行任务：**

#### 构建和推送镜像 (build-and-push)
- 构建后端和前端 Docker 镜像
- 推送镜像到 GitHub Container Registry (ghcr.io)
- 使用语义化版本标签

#### 部署到 Staging (deploy-staging)
- **触发条件：** Push 到 `develop` 分支或手动选择 staging 环境
- SSH 连接到 Staging 服务器
- 拉取最新镜像
- 使用 docker-compose 重启服务
- 健康检查
- 发送 Slack 通知

#### 部署到 Production (deploy-production)
- **触发条件：** 创建版本标签或手动选择 production 环境
- SSH 连接到 Production 服务器
- 备份当前部署状态
- 拉取最新镜像
- 滚动更新（零停机部署）
- 健康检查
- 运行数据库迁移
- 发送 Slack 通知
- 创建 GitHub Release

### 3. 依赖更新检查 (`.github/workflows/dependency-update.yml`)

**触发条件：**
- 每周一早上 8 点自动运行
- 手动触发

**执行任务：**
- 检查后端依赖更新 (`npm outdated`)
- 检查前端依赖更新 (`npm outdated`)
- 检查安全漏洞 (`npm audit`)
- 如果发现高危漏洞，自动创建 Issue

### 4. 自动代码审查 (`.github/workflows/code-review.yml`)

**触发条件：**
- 创建或更新 Pull Request

**执行任务：**
- 检查提交信息格式
- 代码复杂度分析
- 检查大文件（>500KB）
- 检查 TODO 和 FIXME
- 检查调试代码（console.log、debugger）
- PR 大小分析
- 自动添加标签
- 检查 PR 描述完整性

## 环境配置

### GitHub Secrets

需要在 GitHub 仓库设置中配置以下 Secrets：

#### Staging 环境

| Secret 名称 | 说明 | 示例 |
|------------|------|------|
| `STAGING_HOST` | Staging 服务器地址 | `staging.your-domain.com` |
| `STAGING_USER` | SSH 用户名 | `deploy` |
| `STAGING_SSH_KEY` | SSH 私钥 | `-----BEGIN RSA PRIVATE KEY-----...` |

#### Production 环境

| Secret 名称 | 说明 | 示例 |
|------------|------|------|
| `PRODUCTION_HOST` | Production 服务器地址 | `your-domain.com` |
| `PRODUCTION_USER` | SSH 用户名 | `deploy` |
| `PRODUCTION_SSH_KEY` | SSH 私钥 | `-----BEGIN RSA PRIVATE KEY-----...` |

#### 其他配置

| Secret 名称 | 说明 | 是否必需 |
|------------|------|---------|
| `API_BASE_URL` | 前端 API 基础 URL | 是 |
| `SLACK_WEBHOOK` | Slack 通知 Webhook | 否 |
| `SONAR_TOKEN` | SonarCloud Token | 否 |
| `CODECOV_TOKEN` | Codecov Token | 否 |

### 配置 SSH 密钥

1. 在服务器上生成 SSH 密钥对：
```bash
ssh-keygen -t rsa -b 4096 -C "github-actions@your-domain.com"
```

2. 将公钥添加到服务器的 `~/.ssh/authorized_keys`：
```bash
cat ~/.ssh/id_rsa.pub >> ~/.ssh/authorized_keys
```

3. 将私钥内容复制到 GitHub Secrets：
```bash
cat ~/.ssh/id_rsa
```

### 服务器准备

在部署服务器上需要：

1. 安装 Docker 和 Docker Compose
2. 创建部署目录：
```bash
sudo mkdir -p /opt/training-platform
sudo chown $USER:$USER /opt/training-platform
```

3. 克隆项目配置文件：
```bash
cd /opt/training-platform
git clone <repository-url> .
```

4. 配置环境变量：
```bash
cp .env.example .env
# 编辑 .env 文件，配置生产环境变量
```

5. 创建备份目录：
```bash
mkdir -p backup
```

## 部署流程

### 自动部署

#### 部署到 Staging

1. **方式一：推送到 develop 分支**
```bash
git checkout develop
git push origin develop
```

2. **方式二：手动触发**
- 访问 GitHub Actions 页面
- 选择 "CD - 持续部署" 工作流
- 点击 "Run workflow"
- 选择 "staging" 环境

#### 部署到 Production

1. **方式一：创建版本标签**
```bash
# 创建标签
git tag -a v1.0.0 -m "Release version 1.0.0"
git push origin v1.0.0
```

2. **方式二：手动触发**
- 访问 GitHub Actions 页面
- 选择 "CD - 持续部署" 工作流
- 点击 "Run workflow"
- 选择 "production" 环境

### 手动部署

如果需要手动部署：

```bash
# SSH 连接到服务器
ssh user@your-server

# 进入项目目录
cd /opt/training-platform

# 拉取最新代码
git pull

# 拉取最新镜像
docker-compose -f docker-compose.prod.yml pull

# 重启服务
docker-compose -f docker-compose.prod.yml up -d

# 运行数据库迁移
docker-compose -f docker-compose.prod.yml exec backend npx prisma migrate deploy

# 查看日志
docker-compose -f docker-compose.prod.yml logs -f
```

## 故障排查

### CI 失败

#### 测试失败

1. 查看失败的测试日志
2. 在本地运行相同的测试：
```bash
cd backend
npm run test:unit
npm run test:integration
```
3. 修复测试后重新提交

#### 构建失败

1. 检查 TypeScript 类型错误：
```bash
npm run type-check
```
2. 检查 Lint 错误：
```bash
npm run lint
```
3. 修复错误后重新提交

#### Docker 构建失败

1. 在本地构建 Docker 镜像：
```bash
docker build -t test-backend ./backend
docker build -t test-frontend ./frontend
```
2. 检查 Dockerfile 和 .dockerignore
3. 修复后重新提交

### CD 失败

#### SSH 连接失败

1. 检查 SSH 密钥是否正确配置
2. 测试 SSH 连接：
```bash
ssh -i ~/.ssh/id_rsa user@server
```
3. 检查服务器防火墙设置

#### 部署失败

1. 查看部署日志
2. SSH 连接到服务器检查：
```bash
# 查看容器状态
docker-compose -f docker-compose.prod.yml ps

# 查看容器日志
docker-compose -f docker-compose.prod.yml logs

# 检查磁盘空间
df -h

# 检查内存使用
free -h
```

#### 健康检查失败

1. 检查服务是否正常启动：
```bash
docker-compose -f docker-compose.prod.yml ps
```
2. 查看应用日志：
```bash
docker-compose -f docker-compose.prod.yml logs backend
docker-compose -f docker-compose.prod.yml logs frontend
```
3. 手动测试健康检查端点：
```bash
curl http://localhost:3000/health
```

### 回滚部署

如果部署出现问题，可以快速回滚：

```bash
# 查看可用的镜像版本
docker images | grep training-platform

# 回滚到之前的版本
export BACKEND_IMAGE=ghcr.io/your-org/training-platform-backend:previous-tag
export FRONTEND_IMAGE=ghcr.io/your-org/training-platform-frontend:previous-tag

docker-compose -f docker-compose.prod.yml up -d
```

## 最佳实践

### 1. 分支策略

- `main` - 生产环境分支，只接受来自 `develop` 的合并
- `develop` - 开发分支，用于集成功能
- `feature/*` - 功能分支，从 `develop` 创建
- `hotfix/*` - 紧急修复分支，从 `main` 创建

### 2. 提交规范

使用 Conventional Commits 格式：

```
<type>(<scope>): <subject>

<body>

<footer>
```

**类型 (type)：**
- `feat`: 新功能
- `fix`: Bug 修复
- `docs`: 文档更新
- `style`: 代码格式调整
- `refactor`: 代码重构
- `test`: 测试相关
- `chore`: 构建/工具变更

**示例：**
```
feat(backend): 添加用户认证功能

- 实现 JWT 认证
- 添加登录和注册接口
- 添加认证中间件

Closes #123
```

### 3. Pull Request 流程

1. 从 `develop` 创建功能分支
2. 开发并提交代码
3. 推送到远程仓库
4. 创建 Pull Request
5. 等待 CI 检查通过
6. 请求代码审查
7. 解决审查意见
8. 合并到 `develop`

### 4. 版本发布

1. 从 `develop` 创建 release 分支：
```bash
git checkout -b release/v1.0.0 develop
```

2. 更新版本号和 CHANGELOG

3. 合并到 `main` 并打标签：
```bash
git checkout main
git merge release/v1.0.0
git tag -a v1.0.0 -m "Release version 1.0.0"
git push origin main --tags
```

4. 合并回 `develop`：
```bash
git checkout develop
git merge release/v1.0.0
git push origin develop
```

### 5. 监控和告警

- 配置 Slack 通知接收部署状态
- 配置 Sentry 监控生产环境错误
- 定期检查 GitHub Actions 运行状态
- 关注依赖更新和安全漏洞

### 6. 安全建议

- 定期更新依赖包
- 及时修复安全漏洞
- 不要在代码中硬编码密钥
- 使用 GitHub Secrets 管理敏感信息
- 定期轮换 SSH 密钥和 API Token
- 启用双因素认证

## 常见问题

### Q: 如何跳过 CI 检查？

A: 在提交信息中添加 `[skip ci]` 或 `[ci skip]`：
```bash
git commit -m "docs: 更新文档 [skip ci]"
```

### Q: 如何重新运行失败的工作流？

A: 在 GitHub Actions 页面点击 "Re-run jobs" 按钮。

### Q: 如何查看部署历史？

A: 访问 GitHub Actions 页面，选择 "CD - 持续部署" 工作流查看历史记录。

### Q: 如何配置自定义部署环境？

A: 修改 `.github/workflows/cd.yml`，添加新的部署 job。

### Q: 如何禁用某个工作流？

A: 在工作流文件中添加：
```yaml
on:
  workflow_dispatch:  # 只允许手动触发
```
