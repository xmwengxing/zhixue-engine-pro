# 答题区设计方案可行性分析

> 分析对象：`docs/答题区设计方案.md`（电子答题专区完整设计方案）
> 分析方法：方案原文逐模块拆解 → 对照本项目现状（`AnswerZone.tsx` / `answerZoneService.ts` / `services/formula-verify` / 数据模型）→ 对照业界在产方案（Exam.net、MathLive、GeoGebra、Desmos 官方实践）→ 逐项给出可行性与实施建议
> 结论性质：**方案方向正确、整体可行，但存在明显过度设计；约 60% 内容本项目已有基础或应精简，建议分层实施**

---

## 一、总体判断

| 维度 | 结论 |
|---|---|
| 方向 | ✅ 正确：电子答题 + 结构化数据 + 规则引擎优先批改，是解决 OCR 不准/幻觉的根本路径，业界在产系统（如北欧学校用的 Exam.net）正是同一套组合（GeoGebra/Desmos/公式编辑器/手写扫描内嵌为考试工具） |
| 技术选型 | ✅ 大体成立：MathLive（免费开源、活跃维护、2025 仍持续迭代、React/移动端友好）与 GeoGebra/Desmos（教育免费）均为成熟方案 |
| 成本估算 | ⚠️ 明显乐观偏差：方案把 10+ 第三方组件全量纳入（MathLive/GeoGebra/Desmos/tldraw/MyScript/TipTap/sympy/OCR），若照单全收，工作量与商务成本远超"Sprint 2.5/3.5/4.5"暗示的量级 |
| 与现状差距 | ✅ 比方案预期小：项目**已经具备**公式等价判断微服务（`services/formula-verify`，Python sympy）、结构化答题字段（`Answer.answerData/inputMethod`）、题型配置字段（`Question.answerType/answerConfig`）、拍照 OCR 兜底链路；方案中"需要新建的数据库表/字段"大部分已存在 |

**一句话结论：采纳方案的架构与优先级思想，砍掉高成本低 ROI 的手写 SDK 与自由画布，按"公式编辑器 → 交互题型 → 几何/函数 → 手写兜底"四层渐进实施。**

---

## 二、逐模块可行性评估

### 2.1 公式编辑器（方案首选 MathLive）—— ✅ 立即做，P0

| 项 | 评估 |
|---|---|
| 技术成熟度 | 高。免费开源（cortex-js/mathlive），Web Component `<math-field>`，React 集成成熟；内置 800+ LaTeX 命令、虚拟键盘（移动端）、无障碍；支持 LaTeX/MathML/ASCIIMath/Typst/MathJSON 五种格式输出 |
| 本项目差距 | `AnswerZone` 的 FORMULA 题目前是 **LaTeX 纯文本输入**（`<input>` + placeholder 提示），小学生根本不会手写 LaTeX——这是当前最影响体验的短板 |
| 落地 | 新增 `FormulaEditor` 组件（`<math-field>` 包一层），替换 FORMULA/填空题的文本输入；`onChange` 取 `getValue('latex')`；题干公式渲染用 KaTeX（方案正确） |
| 成本 | 1 个组件 + 1 次 npm 依赖 + 按题配置虚拟键盘布局；**无商务成本** |
| 风险 | 低（社区活跃）；注意按需加载（懒加载）避免打包体积膨胀 |

### 2.2 基础客观题（选择/判断/填空）—— ✅ 已有，微调即可

- 现状：`AnswerZone` 已实现 CHOICE / MULTIPLE_CHOICE / JUDGE / FILL（点击/文本输入 + 拍照兜底），规则引擎批改已通
- 建议：填空支持"多空"（`blanks[]`）与"文本+公式混排"（配合 MathLive 单行嵌入）；其余不动

### 2.3 排序题 / 连线题 —— ✅ P1，低成本

- 方案：dnd-kit 拖拽排序、SVG 连线——**无需任何商业 SDK**，免费开源
- 现状：两类题当前都落 `default` 分支（textarea + 拍照，"待批改"）
- 落地：2 个组件（SortingInput / MatchingInput），批改规则引擎比对序列/匹配对
- 成本：约 1-2 人日/组件；风险低

### 2.4 证明题分步输入 —— ✅ P1，用结构化表单替代 SDK

- 方案原文：结构化表单（条件→推理→结论）+ 公式编辑器 + LLM 逻辑链验证
- 评估：**无需第三方 SDK**，就是"多行 MathLive + 步骤列表"；批改走 LLM（现有 AI 链路 `evaluateAnswer` 已有主观题评判能力），比"几何约束验证"简单得多
- 建议：P1 与排序/连线同期；是"第三梯队"里成本最低的一项，可提前

### 2.5 几何作图（GeoGebra 嵌入）—— ⚠️ P2，需部署形态决策

| 项 | 评估 |
|---|---|
| 成熟度 | 高，教育行业标准；国内有镜像站（ggb123.cn）与大量中文课件生态；Exam.net 也内嵌 |
| 模式 | iframe/JS API 嵌入；题目预设用 `appletOnLoad` 命令注入；提交取 `getBase64/getXML` |
| 关键问题 | ① **在线 CDN 依赖**：班级/考试场景需网络稳定，且 ggb 加载慢；建议评估**离线部署**（GeoGebra 支持本地静态资源）② 批改"几何约束验证"（平行/垂直/等长）需自研解析 ggb XML 的逻辑，工作量被方案低估 ③ UI 风格与产品不一致 |
| 建议 | P2；先只对**高频几何题型**（尺规作图）启用；MVP 可先用手写/拍照兜底 + 图形题标注"待批改" |

### 2.6 函数绘图（Desmos API）—— ⚠️ P2 或砍，商务条款先确认

| 项 | 评估 |
|---|---|
| 成熟度 | 高，Desmos 免费且被 SAT/IB 等国际考试采用；2023 新版几何工具 Beta |
| 关键问题 | ① 需申请 **API Key**，商业使用条款必须书面确认（"教育免费"不等于"任意商用免费"）② 中文支持一般 ③ 提交批改（表达式等价/特征点验证）需自研 |
| 建议 | **默认砍掉**：函数绘图题在当前题库占比极低，且可用"输入函数表达式（MathLive）+ 后端 sympy 计算特征点（顶点/零点）"的低配方案覆盖 80% 需求，无需嵌入计算器 |

### 2.7 手写输入（MyScript / MathType Hand）—— ❌ 砍或无限期延后

| 项 | 评估 |
|---|---|
| 成本 | **商业授权、按设备数收费**，方案自己也标注"高风险：成本高，需评估 ROI" |
| 替代 | 项目已有**拍照上传 + 视觉模型识别**（`visionRecognitionController`，`ocr-unlimited` 服务）兜底链路；Canvas 自由手写板（tldraw）只是"画图"，不解决公式结构化 |
| 建议 | **MVP 不引入**。手写场景维持"拍照上传 → 视觉识别 → 结构化/LLM 批改"现状；等产品验证手写是高频刚需、且用户愿意付费时再评估 MyScript |

### 2.8 富文本 + 公式混排（TipTap）—— ⏸ 延后

- 简答题/证明题的"图文混排"目前用 textarea 可接受；TipTap 集成 MathLive 有成熟插件，但属于体验优化，P2 之后再做

## 三、批改引擎与数据模型：方案的两处"过时假设"

### 3.1 批改引擎 —— 方向正确，且项目已落地大半

方案主张"结构化数据 → 规则引擎批改 80%，只有开放题用 LLM"。**项目现状已经实现同一分层**（`answerZoneService.gradeExamPaper`）：

```
客观题（选择/判断）→ 规则引擎精确匹配（0 延迟）
公式题             → services/formula-verify（Python sympy 微服务，代数等价判断，失败降级待批改）
主观/几何/函数     → 标记「待批改」→ 走 LLM 语义评判
```

公式语义比对方案里写"用 sympy"——**项目已建好该微服务**，无需重做。可选增强：接入 `ComputeEngine (MathJSON)` 做前端实时等价预览，属锦上添花。

### 3.2 数据模型 —— 方案要求的新表大部分已存在

方案 SQL 要新建 `electronic_answers` 表、给题目加 `answer_type`/`answer_config`。**项目已经具备等价物**：

| 方案要求 | 项目现状 |
|---|---|
| `answer_type`（题型键） | ✅ `Question.answerType`（已用，驱动输入/批改组件选择） |
| `answer_config`（选项/正确答案/expectedLatex/几何预设） | ✅ `Question.answerConfig`（已用） |
| 结构化答案 `answer_data` | ✅ `Answer.answerData`（Json，按 answerType 组织） |
| `input_method` | ✅ `Answer.inputMethod`（click/keyboard/formula/geogebra/desmos/handwriting/photo 枚举已定义） |
| `electronic_answers` 独立表 | ❌ 不需要：`Answer` 表即答题记录表，天然承载 |

**结论：数据层零新增，方案假设滞后于现状——进一步印证落地面比方案预期小。**

## 四、业界对标（支撑"方向可行"）

- **Exam.net**（北欧学校在产在线考试系统）：考试工具包 = GeoGebra + Desmos + 公式编辑器 + 绘图工具 + 手机扫码拍照上传手写答卷 + 语音作答——**与方案组件清单几乎一一对应**，证明组合是行业成熟做法
- **MathLive**（cortex-js）：2025 年仍在持续迭代，免费开源，社区活跃（CSDN/掘金大量中文实践），是"公式输入"事实标准之一
- **Desmos vs GeoGebra**：Desmos 函数/代数更强、学习曲线低、全免费；GeoGebra 几何/3D/CAS 更强、离线可用、LMS 集成成熟——方案"GeoGebra 几何 + Desmos 函数"的分工合理，但**两者择一嵌入即可覆盖 80% 场景**，不必都上

## 五、结论与建议实施路线

### 结论

1. **方案方向与架构正确、整体可行**，且项目已有约 40% 基础设施（sympy 微服务、结构化字段、OCR 兜底、答题区骨架）
2. **按方案全量落地不划算**：10+ 第三方组件中，MyScript（商业）、Desmos（API Key/条款）、TipTap（体验优化）、tldraw（兜底增强）四项应砍/延后，可削减约 60% 工程量与全部商业成本
3. 数据模型**无需新增任何表**；批改分层已落地，剩余是"按题型补齐输入组件"

### 建议路线（与现有开发节奏对齐）

| 阶段 | 内容 | 依赖/成本 |
|---|---|---|
| **P0（建议立即排期）** | ① MathLive 公式编辑器（替换 FORMULA/填空的 LaTeX 文本输入，含虚拟键盘）② KaTeX 渲染题干公式 ③ 多空填空 | 仅 1 个 npm 依赖，免费，1.5-2 人日 |
| **P1** | ① 排序题拖拽（dnd-kit）② 连线题（SVG）③ 证明题分步输入（多行 MathLive + 步骤列表，LLM 批改） | 免费开源，3-4 人日 |
| **P2（需商务/产品确认）** | ① GeoGebra 几何嵌入（先定 CDN/离线部署形态；批改只做"约束验证"最简版或先待批改）② 函数绘图低配版（MathLive 输入 + sympy 特征点校验），Desmos 视条款再定 | GeoGebra 教育免费；Desmos 需 API Key |
| **不做（明确砍掉）** | MyScript / MathType Hand 手写 SDK（商业成本高，拍照 OCR 已兜底）；tldraw 自由画布（拍照兜底已覆盖）；TipTap 富文本混排（text 输入可用） | — |

> 若只做 P0+P1，即可覆盖"选择/判断/填空/公式/排序/连线/证明/简答"全部题型的结构化作答，且**零新增商务成本**；几何/函数/手写三大难点的当前形态（拍照+待批改）在 P0/P1 期间维持不变。

---

*分析基于 2026-08-04 项目代码现状与公开资料；商务授权（Desmos API Key、GeoGebra 商用条款）建议在 P2 排期前由产品正式向官方确认。*
